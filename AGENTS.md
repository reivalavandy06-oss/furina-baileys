# AGENTS.md

Guide for AI coding agents (Claude Code, Cursor, Aider, Codex, Copilot Workspace, etc.) contributing to Furina-Baileys. Human contributors should also read this — there's nothing AI-specific in the conventions, only in the disclosure rules at the end.

If you are an AI agent driving this repo, read this file first, then `CODE_OF_CONDUCT.md` (specifically the AI policy section), then `SECURITY.md`.

## What this repo is

A **fork of Baileys** — the TypeScript WebSocket client for the WhatsApp Web protocol (no browser, no Selenium; it speaks the binary Noise/protobuf protocol directly) — published to npm as **`@vanzzz/furina-baileys`**. On top of upstream it adds the production layers downstream bots actually need: CRM broadcast with anti-ban rate limiting, delivery tracking, a connection stability manager, an antiban toolkit, interactive buttons/carousel builders, and a LID↔PN identity resolver. It replaced the old unscoped `furina-baileys` package (still installable, deprecated path for migration docs).

The library is **dual-use**: legitimate automation, bots, and integrations on one side; spam, stalkerware, and ToS-breaking automation on the other. We do not accept contributions whose primary purpose is to enable abuse (mass messaging, evasion of WhatsApp's anti-spam, scraping users without consent). See `CODE_OF_CONDUCT.md`.

## Repository layout

```

  Signal/          Signal Protocol session/sender-key wrapping over libsignal-node
  WABinary/        Binary node encoding/decoding + the canonical JID helpers
  WAUSync/         USync query protocols
  Types/           Public TypeScript types — touching these is a public-API change
  Defaults/        Constants (WA Web version, default config)
  Utils/           Shared engine code — decoding, media, auth state, retry, generics
    crm/             CRM + broadcast: manager.ts, customer/conversation/analytics,
                     broadcast/{manager,tracker,health,channel,segment,template,
                     quarantine,registry}.ts, storage/ (interface + in-memory)
    antiban/         Anti-ban toolkit: profiles, timing, limiter, health
    stability/       Connection stability manager: backoff, stealth, session
    messaging/       Buttons, carousel, MessageBuilder, button tracker
    member-labels.ts / lid-resolver.ts / furina-resolver.ts / use-multi-file-auth-state.ts
  __tests__/       Jest unit + integration tests, colocated by area; e2e in __tests__/e2e
WAProto/           Generated protobuf bindings — DO NOT hand-edit
docs/              Long-form documentation (12 files, index.md is the landing page)
Example/           Reference implementation in example.ts
engine-requirements.js  Preinstall gate: hard-fails Node < 20
.yarn/releases/    Committed Yarn 4.9.2 binary — the canonical runtime (see Setup)
```

`WAProto/index.js` / `WAProto/index.d.ts` are generated by `WAProto/GenerateStatics.sh`. If a change requires modifying them, regenerate via `yarn gen:protobuf` rather than editing by hand.

## Setup and environment

- **Node ≥ 20** — enforced twice: `engines`, and `engine-requirements.js` on `preinstall` (exits 1 below 20).
- **Yarn 4.9.2 is committed** at `.yarn/releases/yarn-4.9.2.cjs`, wired via `yarnPath` in `.yarnrc.yml`. Corepack is *not* required. The canonical invocation, which works everywhere including CI:

```bash
node .yarn/releases/yarn-4.9.2.cjs install
```

- **proot/Termux gotcha:** Corepack itself crashes there (`Dynamic require of "util" is not supported`). If bare `yarn` fails in such an environment, don't debug the repo — invoke the committed binary directly.
- **Never install this repo with npm.** The 27 `resolutions` entries in package.json are a Yarn feature; npm reads `overrides`, which this repo does not define, so under npm every one of those CVE patches silently no-ops. `package-lock.json` is gitignored on purpose — two lockfiles = drift.
- `yarn.lock` is committed. Any dependency change must keep `install --immutable` green.

## Daily commands

| Task | Command |
|---|---|
| Install | `node .yarn/releases/yarn-4.9.2.cjs install` (CI/verification: add `--immutable`) |
| Type-check + lint | `node .yarn/releases/yarn-4.9.2.cjs run lint` |
| Full test suite | `NODE_OPTIONS="--max-old-space-size=1024" node .yarn/releases/yarn-4.9.2.cjs run test --runInBand` |
| One test file | `node --experimental-vm-modules node_modules/jest/bin/jest.js --runInBand --testMatch '**/<name>.test.ts'` |
| Build (lib + types) | `node .yarn/releases/yarn-4.9.2.cjs run build` |
| Run the example | `node .yarn/releases/yarn-4.9.2.cjs run example` |
| Regenerate protobufs | `node .yarn/releases/yarn-4.9.2.cjs run gen:protobuf` |
| Audit deps | `node .yarn/releases/yarn-4.9.2.cjs npm audit --recursive` |
| e2e tests | `run test:e2e` — requires the bartender mock server |

Notes that will bite you:

- `yarn lint` runs `tsc` first, then ESLint. A green lint means no type errors.
- Passing your own `--testMatch` to jest **replaces** the one baked into the `test` script — that's exactly how the single-file recipe above works.
- `--runInBand` + `--max-old-space-size=1024` is the low-RAM serial recipe (phones/proot). Do not insert `--` before `--runInBand` when going through the yarn script.
- Lint carries ~1300 **pre-existing warnings** (mostly legacy `any`s). The gate is **0 errors**. Never run mass lint auto-fixes (`lint:fix` touches everything); keep diffs focused.

## Code style

- **TypeScript strict** — `strict`, `strictNullChecks`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax` are all on. Don't disable them locally. (The two build tsconfigs relax `verbatimModuleSyntax` for emission; the source-tree rule still applies to what you write.)
- **Tabs** for indentation, single quotes, no semicolons (Prettier-enforced).
- **No `any` in new code.** Existing `any`s are tolerated as warnings, not invitations.
- **No comments that restate the code.** Comment the *why* — protocol quirks, WhatsApp-side behavior, non-obvious workarounds.
- **No emojis in code or commit messages** unless the user explicitly asks.
- **Named exports** preferred. Default exports only where they already exist (e.g., `makeWASocket`).
- **Errors**: throw `Boom` (`@hapi/boom`) for protocol/HTTP-style errors so downstream code can branch on `.output.statusCode`. Plain `Error` for everything else.
- **Logging**: code paths that cross async boundaries should accept a `logger: ILogger` (pino-compatible). Don't `console.log` in library code (the CRM/broadcast modules predate this rule and still use `console.warn` — match the module you're in rather than mixing styles inside one file).

## Idiomatic patterns

These are the patterns the existing code uses. Match them. New code that does the same thing differently will get review comments asking you to align.

### Errors — Boom with statusCode

```ts
import { Boom } from '@hapi/boom'

if (!sock.user) {
	throw new Boom('Not authenticated', { statusCode: 401 })
}

if (!isJidUser(jid)) {
	throw new Boom(`Invalid jid: ${jid}`, { statusCode: 400 })
}
```

Downstream code branches on `error.output.statusCode` to retry, log out, or surface to the user. Plain `throw new Error(...)` loses that signal.

### Logging — structured, never positional

```ts
// good: object first, message last; reads cleanly in JSON logs
logger.warn({ msgId: attrs.id, from: attrs.from }, 'error 463: account restricted')
logger.error({ err: error, opName }, 'failed to parse mex notification JSON')

// bad: string interpolation, untyped fields
logger.warn(`error 463 from ${attrs.from}`)
console.log('failed:', error)
```

Pino convention: errors go under `err`, not `error` or `e`. The structured object is the *first* argument.

### JIDs — always go through the helpers

```ts
import { jidDecode, jidNormalizedUser, areJidsSameUser, isJidUser } from '../WABinary'

const decoded = jidDecode(rawJid)            // { user, server, device?, agent? } | undefined
const normalized = jidNormalizedUser(rawJid) // strips device/agent suffix
const same = areJidsSameUser(a, b)           // compares user portions only
```

Never split a JID with `.split('@')` or compare with `===`. JIDs carry device suffixes (`:0`, `:42`), agent fields (`user_1`), and LID/PN duality — string ops silently miss matches and ship bugs that only fire on multi-device accounts. **Every identity key** (CRM customer, quarantine entry, member-labels entry, tracker record) must be the canonical `jidNormalizedUser()` form.

### Binary nodes — typed accessors

```ts
import { getBinaryNodeChild, getBinaryNodeChildren, getBinaryNodeChildString } from '../WABinary'

const groupsNode = getBinaryNodeChild(result, 'groups')
if (!groupsNode) {
	throw new Boom('missing <groups> in iq response', { statusCode: 502 })
}
const groups = getBinaryNodeChildren(groupsNode, 'group') // BinaryNode[]
```

Don't reach into `node.content` as an array directly — the accessors handle the missing/single/array cases.

### Sending IQs — `query` with timeouts

```ts
const result = await sock.query({
	tag: 'iq',
	attrs: { to: S_WHATSAPP_NET, type: 'get', xmlns: 'w:profile:picture' },
	content: [{ tag: 'picture', attrs: { type: 'image', query: 'url' } }]
}, /* timeoutMs */ 15_000)
```

`query` auto-generates the stanza id, attaches a one-shot listener, rejects on timeout. Don't hand-roll `sock.ws.send` + manual listeners — you'll leak them.

### Listening for incoming stanzas — `CB:` prefix

```ts
sock.ws.on('CB:ib,,dirty', async (node: BinaryNode) => { ... })
sock.ws.on('CB:notification,type:server_sync', handler)
```

The `CB:tag,attr:value` syntax routes by tag + attribute filter inside the websocket. Don't filter manually inside a generic `'message'` handler.

### Public events — `ev.on`, dedupe handlers

```ts
sock.ev.on('messages.upsert', ({ messages, type }) => { ... })
sock.ev.on('creds.update', saveCreds)
```

Registering `saveCreds` (or any handler) twice means writing twice. The harness in `__tests__/e2e/helpers/test-client.ts` shows the cleanup pattern (`ev.off` in teardown).

### Async cleanup — bracket pattern

When you allocate a resource (timer, listener, ws subscription) inside a Promise, clean it up in *both* paths — resolve and reject. Half-cleanups are how this codebase grew its memory leaks; see `waitForChannelPost` in `crm/broadcast/channel.ts` for the shape (define `cleanup` first, call it from every exit).

### Imports — `verbatimModuleSyntax`

```ts
import type { WAMessage, WAUrlInfo } from '../Types'
import { Boom } from '@hapi/boom'
import { type BinaryNode, getBinaryNodeChild } from '../WABinary'
```

Type-only imports must be marked `import type` or inline-prefixed `type`, or the build fails.

### Optional chains over null guards

`noUncheckedIndexedAccess` is on, so indexing returns `T | undefined`. Prefer `msg.message?.extendedTextMessage?.text ?? …`. Don't paper over it with `!` unless the type system can't see the invariant — then leave a one-line comment saying why.

### Furina runtime patterns

These came out of real leak/race bugfixes. New manager/limiter code must match them:

- **Listener lifecycle:** long-lived managers store `sock.ev` handlers as instance fields and expose an idempotent, instance-scoped `dispose()` that removes only its own handlers via `ev.off(event, handler)` — never `removeAllListeners`, never raise `setMaxListeners`. If a constructor auto-attaches, a public `attach()` must be a no-op when already attached. Owners cascade: `CRMBroadcastManager.dispose()` disposes its `CRMDeliveryTracker`. See `crm/manager.ts`, `crm/broadcast/{manager,tracker}.ts`, `messaging/button-tracker.ts`.
- **Rate limiter claim/release:** claim the slot *synchronously at check time* — no `await` between check and record, or two parallel callers both pass the check and breach the limit. Release the slot when the attempt doesn't consume budget (dry-run, failed send, non-member). Keep the old wait-vs-skip behavior: the per-minute limiter blocks until a slot frees; the hourly one returns null and the caller reports `throttled`. See `claimMinuteSlot`/`releaseMinuteSlot` and `claimHourSlot`/`releaseHourSlot` in `crm/broadcast/manager.ts`.
- **Bounded buffers:** any append-only map/array gets a FIFO cap and prunes lazily on read/write — never via `setInterval`. Existing caps: `MAX_PENDING_UPDATES = 200` (tracker), `MAX_RISK_EVENTS = 200` (health monitor), `DEFAULT_MAX_ENTRIES = 500` (button tracker), `maxConversationHistory` (conversation memory).
- **Monotonic state machines:** delivery status flows through `toStatus()` + rank comparison in `crm/broadcast/tracker.ts` — a late SERVER_ACK never downgrades a `read`, and status 0 (error) is terminal. Health-guard risk per content window fires once (latched per window entry, re-armed when the window expires).

## Public API discipline

`src/Types/**` and the `src/index.ts` re-exports (which pull in the furina modules via `./Utils`, `./Utils/furina-resolver`, `./Utils/antiban`) define the public surface. Treat changes there as breaking unless you can prove additive-only.

`files` in package.json controls what npm ships: `lib/**/*`, `WAProto/**/*`, `LICENSE`, `README.md`, `CHANGELOG.md`, `engine-requirements.js`. `docs/` is intentionally excluded — the npm page stays light, long-form docs live on GitHub. When you add or change a user-facing feature, update both the short README section and the matching `docs/*.md` page.

For wire-level changes (`Socket/messages-recv.ts`, `Utils/decode-wa-message.ts`, `WABinary/`, etc.) — describe the WhatsApp-side trigger in the PR. Reviewers can't always reproduce protocol behavior, so the description does the heavy lifting.

## Publishing

- **Method:** GitHub Actions + npm Trusted Publishing (OIDC) — no `NPM_TOKEN` secret anywhere. `.github/workflows/publish.yml` triggers on `workflow_dispatch` only, with `contents: read` + `id-token: write`, upgrades runner npm to 11 (OIDC support), installs via the committed Yarn binary, builds, then `npm publish --access public`.
- **One-time npmjs.com setup:** the first publish must be manual (`npm publish --access public` by the account owner) to create the `@vanzzz` scope. Then on the package's Settings page register the trusted publisher: Provider `GitHub Actions`, org `reivalavandy06-oss`, repo `furina-baileys`, workflow `publish.yml`, environment empty.
- **Never push a `v*` tag.** `publish-release.yml` (upstream leftover) triggers on `v*` tag pushes and publishes this code as **`baileys`** and **`@whiskeysockets/baileys`** — the wrong package names, on whatever credentials the runner has. Until that workflow is removed or neutered, tags are radioactive.
- `npm publish` runs `prepare` → `yarn build`, so the tarball is always built fresh. Bump `version` in package.json, push, then run the workflow.

### Verify a publish like a user would

`npm view` is not enough — always smoke-test in an empty directory:

```bash
mkdir /tmp/fresh && cd /tmp/fresh && npm init -y >/dev/null
npm install @vanzzz/furina-baileys
node -e "const b=require('@vanzzz/furina-baileys'); console.log(typeof b.makeWASocket)"
printf "import m from '@vanzzz/furina-baileys'\nconsole.log(typeof m)\n" > t.mjs && node t.mjs
```

Both the CJS `require` and the ESM `import` must load. The dual build ships one shared `lib/WAProto` copy (ESM source) referenced from both the `lib/cjs` and `lib/esm` trees; Node's module-syntax detection is what makes that work — pinning a root `"type"` field has broken exactly this in a published version before. Any change near `type`, `main`, `module`, `exports`, or the build layout requires the fresh-install smoke test above.

## What not to touch without coordination

- **`libsignal` cryptographic flows** — session state, prekeys, sender-key derivation. Subtle bugs here are silent and brick downstream sessions.
- **`Defaults/baileys-version.json`** — bumped by the `update-version` workflow. Manual edits race with automation.
- **`WAProto/` generated files** — regenerate, don't hand-edit.
- **`.github/workflows/`** — CI changes are reviewed separately; bundle them in their own PR when possible. `publish-release.yml` is a misfire hazard (see Publishing).
- **`package.json` `resolutions`** — 27 patches for known advisories, Yarn-only (see Setup). Check `yarn npm audit --recursive` before pruning; removing entries reintroduces CVEs.
- **`package.json` `type` / `main` / `module` / `exports`** — the dual CJS/ESM wiring is load-bearing and has broken a published release before. Any change here requires the fresh-install smoke test from the Publishing section.

## Testing expectations

- Baseline at time of writing: **44 suites / 620 tests**, all green. Your change must not regress it.
- Tests are colocated by area: `src/Foo/bar.ts` → `src/__tests__/Foo/bar.test.ts`. Broadcast tests live in `src/__tests__/Utils/crm/broadcast/`.
- Unit tests mock the socket with a plain `EventEmitter` — no network, no WhatsApp servers.
- New public API → unit test in `src/__tests__/`. New protocol path or stanza handler → integration test mocking the binary node, *not* e2e (e2e is expensive and flaky in agent loops). New crypto/auth flow → e2e against bartender if feasible, otherwise a deterministic fixture test.

### Fake-timer gotchas (learned the hard way)

The rate-limiter and tracker tests freeze time; three pitfalls:

- To drive code that loops `await sleep(...)`, use `jest.useFakeTimers()` + `await jest.advanceTimersByTimeAsync(ms)`. The *synchronous* `advanceTimersByTime` does **not** flush microtasks, so any loop that schedules its next timer inside a promise stalls forever and the test times out.
- `doNotFake: ['setTimeout', ...]` makes sleeps resolve **instantly (0 ms)** — it looks like "real timers" but isn't. Only use it when you need `Date.now` frozen and there is no wait loop to exercise.
- A waiter whose deadline never moves will spin forever. Freeze with `jest.setSystemTime(...)`, then step the clock explicitly — see `per-minute-quota.test.ts` for the driver pattern.

### Broadcast-manager test config

- Pass `minDelayMs: 0, maxDelayMs: 0, newChatPenaltyMs: 0` — otherwise `send()` sleeps 1.5–5 s of real time per recipient.
- `maxRetries: 0` for failure paths, or retry backoffs add real 2s/4s sleeps.
- Give every send **unique content**: the identical-message health guard fires at 4 identical messages in the window and pauses the campaign — which is usually not the thing under test. (`dry-run-health-guard.test.ts` covers the guard itself.)
- Registry and quarantine write JSON files. In tests pass `registryPath: null` and `quarantinePath: null` (or a tmpdir) — never the defaults, which write into the repo root.

### Prove the fix

When you add a regression test, run it once against the pre-fix code — e.g. `git show HEAD:path.ts > path.ts`, run the suite, restore. It must fail there and pass after. A regression test that passes on both sides proves nothing.

## Security-sensitive changes

If your change touches:
- Auth state read/write, key storage, prekey/session lifecycle
- Message decryption / signature verification
- Any path that handles user PII (phone numbers, JIDs, message content) in logs or errors

…flag it explicitly in the PR description. See `SECURITY.md` for disclosure of vulnerabilities (do not file them as public issues).

## AI agent etiquette

Beyond the AI policy in `CODE_OF_CONDUCT.md`:

- **Read before you write.** This codebase has subtle protocol invariants. A grep-and-replace agent will make a mess of `Socket/messages-recv.ts`. Read the surrounding handler before editing.
- **Don't invent WhatsApp protocol details.** If you're not sure how a stanza is structured, find a real example in the tests or in `Utils/decode-wa-message.ts`. Hallucinated XML attributes get merged and then break in production.
- **Verify claims against code before writing them down.** Docs in this repo have claimed features that don't exist (plugin systems, TTS) and Node versions that contradict `engines`. Count the union members, grep the export, run the snippet.
- **Stay in scope.** A bug fix doesn't need a refactor pass. A type tweak doesn't need a comment cleanup PR.
- **Don't paste auth state into AI tools.** `auth_info/` contains long-lived Signal keys. Treat it like an SSH private key.
- **Disclose AI authorship in PRs.** A one-line "drafted with [tool], reviewed by [human]" is enough. See `CODE_OF_CONDUCT.md` § AI Policy for the full rule.

## Commits and PRs

Conventional commits, scoped where useful:

```
fix(broadcast): enforce rolling hourly send limit
docs(readme): update package documentation for 1.1.0-furina
chore(release): prepare npm trusted publishing workflow
```

Before opening a PR:
1. `lint` — must be 0 errors.
2. Full test suite — must be all green. If you can't run e2e locally, say so in the PR description.
3. Don't commit `auth_info*/`, `.env`, `baileys_store*.json`, or any session state.
4. Don't commit a lockfile from a different package manager. If your `yarn.lock` diff is unexpectedly large for a small `package.json` change, you're using the wrong Yarn.
5. Don't push `v*` tags (see Publishing).
